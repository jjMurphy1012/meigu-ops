# Mode: review — 周期复盘与规则审计

**这是自我进化闭环的收口环节。** 日志(`journal`)记录发生了什么,复盘负责回答
**"我这套规则本身对不对"**,并把结论写回 `config/rules.toml`。

触发时机:周五收盘后、月末、一轮明显行情结束时、或用户说"复盘 / 总结 / 反思"。

**产出:** 更新 `config/rules.toml` 的规则状态与证据 + `data/lessons.md`(用户层)。

> 本仓库不提供任何交易策略。这里审计的是**你自己**写在 `config/rules.toml` 与
> `modes/_strategy.md` 里的规则。两个文件都不存在时,先提示用户建立它们
> (`cp config/rules.example.toml config/rules.toml`),不要代为编造。

---

## Step 1 — 拿数据,不靠印象

```bash
make stats                                     # 全期 + 规则审计
python3 scripts/stats.py --since 2026-08-01    # 指定区间
make dashboard                                 # 纪律页同样的审计,可视化
```

再读 `data/journal.md` 最近区间的条目,并用 `get_pnl_trade_history` /
`get_realized_pnl` 与券商记录交叉核对。

> **复盘最大的陷阱是凭印象。** 人会记住痛的和爽的,忘掉大量平淡的正确决策。
> 先看数字,再看叙事。

## Step 2 — 逐条过规则审计结果

审计器对每条规则给出六种判定之一:

| 判定 | 含义 | 该做什么 |
|---|---|---|
| 🔒 程序强制 | 由 `preflight` 某道闸门保证 | 确认该闸门仍存在且未被绕过 |
| ✅ 支持 | 台账数据支持,且前后两段一致、差异超过噪音 | `hypothesis` 可升为 `supported` |
| ❌ 不支持 | 数据与规则相反,**且前后两段都不支持** | 修正判定标准,或降为 `refuted` |
| 🔀 **环境可能变了** | 前后两段结论**相反** | **禁止改状态**。补一个适用环境的条件,分环境重新计数;要停用就降 `provisional` |
| … 数据不足 | 样本太少、标签无归集,或**差异在噪音范围内** | 继续记录,**不要在这里下结论** |
| 👁 需人工核查 | 无法自动化 | 按 `test.how` 亲自过一遍 |

**四道关卡缺一不可:** ① 样本量(≥10 谈方向 / ≥20 谈改状态)
② 前后两段一致(否则是环境问题,不是规则问题)
③ 信噪比(≥1.0 谈方向 / ≥2.0 谈改状态)
④ 最近 2 次审计同向(`data/audit-log.jsonl` 里有历次判定)。

> **"这周赚钱了所以规则对"是错的** —— 运气、环境、样本太少,任何一个都能造出那个结论。
> 一次反转只会让规则回到观察期,不会被判死:**判"规则错了"的门槛必须高于判"没用"。**

**处理原则:**

- **样本不足时不要升级规则。** 拿两三笔盈利去"验证"一条你本来就相信的规则,
  是自我进化机制最容易退化的方式 —— 审计器会拒绝在样本不足时下结论,不要绕过它。
- **`refuted` 不要直接删。** 保留记录,免得半年后再把同一条规则当新发现写一遍。
- **`enforced` 的规则不需要每次复盘都看** —— 有程序兜着。但要确认程序本身还在。

## Step 3 — 三类错误分类

把区间内所有"事后看不该做"的决策分成三类,**处置方式完全不同**:

| 类型 | 定义 | 处置 |
|---|---|---|
| **判断错** | 依据充分、流程正确,但市场走了另一边 | **不改规则**。这是交易的正常成本,改规则等于过拟合到噪音 |
| **纪律错** | 规则说了但没执行 | 不改规则,**加检查点或脚本硬闸门**(能进 `preflight` 的就进) |
| **规则错** | 严格照规则执行,结果系统性变差 | **改规则**,并在该规则的 `evidence` 写清为什么 |

> 分错类型的代价很实在:把"判断错"当成"规则错"去改规则,会让你的纪律随市场噪音漂移;
> 把"纪律错"当成"规则错",会让你不断放宽本来正确的规则,直到它形同虚设。

## Step 4 — 反向审计:漏掉的机会

只审计"做错的"会让系统单调地越来越保守。所以必须对称地问:

- 区间内**你的标的池里涨得最好的**,你有没有持仓?没有的话,是哪条规则挡住的?
  那条规则是不是太严?
- 有多少个检查点是"零操作",其中多少是**具体排查后的结论**、多少是**默认不动的惯性**?
  (`zero-action-must-be-a-conclusion` 这条规则的人工核查就在这里做)
- 现金/BP 在区间内的平均水平 vs 你设的目标 —— **闲置也是亏损**,只是不出现在盈亏表里。
- 有没有连续多个检查点反复评估同一候选却始终没成交?

## Step 5 — 写回

### 5.1 更新 `config/rules.toml`(★ 闭环的关键一步)

对每条被审计的规则:

**全部用脚本改,不要手编 TOML:**

```bash
# 1) 追加证据(免批准)
python3 scripts/rules.py --record-evidence <id> "2026-08-19 …"

# 2) 改状态 —— 必须先得到用户明确批准,再加 --approved
python3 scripts/rules.py --set-status <id> supported --approved --note "理由"

# 3) 新增假设(默认 hypothesis → observe,只能用最低档尺寸)
python3 scripts/rules.py --add-rule <id> "一句能被证伪的话"
```

`--set-status` 不带 `--approved` 会直接退出并提示 —— **状态变更改变的是这条规则
能否指导真钱下单,那是用户的决定,不是你的**。先摆出数据与建议,等确认。

降级为 `refuted` / `retired` 时脚本会自动把 `execution_scope` 设成 `none`,
避免出现"状态说停用、作用域还在跑"的不一致。`last_audited` 也由脚本更新。

### 5.2 同步 `modes/_strategy.md`

`rules.toml` 是可检验的骨架,`_strategy.md` 是完整思路。改了一处要同步另一处,
否则 AI 决策时读到的和审计时检验的会是两套东西。

### 5.3 追加 `data/lessons.md`

本期档案(倒序):区间、组合表现 vs 基准、关键决策清单、三类错误分类结果、
漏掉的机会、下期要改的**一件事**。

> **策略变更不进 `CHANGELOG.md`** —— 那是系统层的版本日志。你的纪律演进
> 记录在规则的 `evidence` 与 `data/lessons.md` 里(都已 gitignore)。
