# _mechanics — 平台机制与执行陷阱(所有 mode 共读)

> 这里只有**平台事实**:券商的订单机制、结算规则、以及 AI CLI + 自动化环境
> 会以什么方式把一个正确的决策变成一次失败的执行。
>
> **这里没有任何交易策略。** 什么时候买、什么时候减、现金留多少、怎么分散 ——
> 全部由你自己写在 `modes/_strategy.md` 与 `config/rules.toml`(都已 gitignore)。
> 仓库只提供模板与问题:`modes/_strategy.example.md`、`config/rules.example.toml`。
>
> 下面每一条都对应一次真实发生过的故障。为保护隐私,只保留**故障形态与对策**,
> 不含具体日期、标的与金额 —— 机制类主张只需要证明"这个故障存在",不需要交易细节。

---

## §1 时段与订单类型

**任何检查点在交易时段内都可以买、可以卖**,唯一门槛是判断合理、有依据。
本项目不按时间点限制操作类型 —— 那属于策略,写在你自己的规则里。

只保留**物理机制**限制,因为它们是事实而非选择:

- **市价单只在正常时段(9:30–16:00 ET,半日市到 13:00)成交。**
- **延长时段(盘前约 7:00–9:30、盘后约 16:00–19:30 ET)只接受限价单**,
  且该标的必须在券商的延长时段合格清单内(按流动性逐一裁定)。
- **24 小时市场仅限整股**,分数股不可用。

所以"盘前用市价单下不了"的原因是**订单类型不匹配时段**,不是策略禁止;
改成合格标的的限价单则可能可以成交。

> ⚠️ **这一段是券商能力,会变,必须探测而不是假设。**
> 早期版本曾把"分数股只能市价单 + 正常时段"写成绝对物理事实,并让若干纪律
> 建立在它之上。这是错的 —— **一条错误的"物理事实"会静默地为策略提供正当性。**
> 下单前用 `get_equity_tradability` 核实该标的在目标时段的可交易性与可用订单类型。

**正常时段用市价单意味着没有价格保护**,这是小仓位的主要成本来源。
这一点与时段规则无关,始终成立。

## §2 结算与订单标识

- **现金账户卖出资金 T+1 结算。** 卖出后 `cash` 立刻上升,但 `buying_power` 要到次日
  才反映 → **当天卖的钱当天不能全部再买**。买入必须看 `buying_power`,不是 `cash`。
- **每笔下单用全新 UUID 作 `ref_id`**(`uuidgen`);只有重试同一笔时才复用(幂等)。
- 下单返回 `state: unconfirmed / queued` **≠ 已成交**;隔几十秒用
  `get_equity_positions` 核对**实际成交价与股数**,不要用下单时的报价当成交价。

## §3 ★ 报价时间戳熔断(救过真金白银)

**`place` 前必须核对 `review` 返回的报价时间戳**(`market_data_disclosure` 里的
"Updated X PM ET" / venue 时间)。

分析与下单之间机器可能休眠数小时,系统时钟醒来前还停在旧时刻 ——
**券商服务器时间戳是唯一可信时钟。**

时间戳与预期偏差大 → **立即中止、重新分析**。
曾据此发现机器已休眠、市场早已收盘,刹住了一张会排进次日开盘的市价单。

配套的**意图过期规则**:交易决策只在有限时间窗内有效
(`execution.intent_ttl_minutes`)。会话解冻/恢复后**严禁执行陈旧意图**,必须重新分析。

两条都已由 `scripts/preflight.py` 强制,不依赖自觉。

## §4 机器与环境

- **交易时段机器必须真正醒着 —— AC 电源不够,合盖照睡。** 电池模式闲置约 1 分钟即休眠。
  同一笔减仓曾连续两天被休眠截杀在 `review` 与 `place` 之间。
  - 防线:LaunchAgent 常驻 `caffeinate -is`(RunAtLoad + KeepAlive,无需 sudo),
    插电/电池下均阻止**闲置**休眠。
  - **残余缺口:`caffeinate` 挡不住物理合盖。** 彻底根治需
    `sudo pmset -a disablesleep 1` 或保持开盖。
  - 盘前必查:`pgrep -x caffeinate` + `pmset -g batt` → `make doctor` 已覆盖。

- **系统时区会漂移,且调度器不跟随本地时钟。** 调度器按**会话启动时区**解读表达式,
  并观察到约 +30 分钟的固定滞后。规则:
  ① 表达式按 ET 目标时刻加 `schedule.cron_offset_minutes` 补偿;
  ② 每条调度 prompt 用 `TZ=America/New_York date` 核对 ET 实际时间;
  ③ 时区再漂移无需改表达式,但要验证滞后规律是否仍成立。

- **session-only 调度只在当前会话存活**,关窗口即丢。跨会话持久化需用云端 routine。

- **手动 /compact、切模型、上下文续接都可能把 session 调度全部清空。**
  曾实测:压缩 + 切模型后调度列表变空,一个检查点静默未触发。
  → **凡遇会话压缩/切模/续接,下一次响应先自检调度列表,缺了立即重建全套节奏。**

- **策略授权 ≠ 工具放行。** 未进权限白名单的 MCP 工具每次调用都弹确认框,
  用户不在场就无限等待 —— 曾被误判为"MCP 挂起数小时",实为权限弹窗等人,
  **弹窗期间整个会话冻结、后续检查点全被阻塞**,损失一整个交易日。
  开启自动交易前必须核查这一层(`.claude/settings.local.json` 需放行
  review / place / cancel / get_equity_orders)。
  用户侧兜底:界面卡住超过十分钟按 **Esc** 解冻(会话与调度不丢)。

- **MCP 工具偶发超时**:曾挂起约 950–1050 秒后自动 abort。非休眠、非权限、非时区,
  原因未知。处置:**直接重试即可自愈**;同一工具反复超时才升级调查。

## §5 每个检查点开始的固定动作

1. `date` + `TZ=America/New_York date` 核对实际时间 vs 计划时刻。
2. `get_equity_orders`(当日)核对真实成交 —— **不要基于记忆里的持仓做决策**。
3. 迟到分级处置:
   - 小幅迟到 → 正常执行。
   - 迟到较多但仍在本点职责窗口内 → 重新拉行情,谨慎执行。
   - 已接近/越过下一检查点 → **不自动跳过**:重新拉最新行情,判断依然合理有依据就
     正常执行,并在汇报里说明实际执行时刻与是否有新信息。若重看后判断已过期,才不执行。
   - **已过收盘 → 禁止任何交易,只汇报。** 这是市场物理事实,不因规则放宽而改变。

## §6 触发线的可判定性

触发线除了"设在哪"(策略),还有一个纯操作层面的属性:**它是否可判定**。

一条线如果经常引发"这算不算破位"的争论,那么它在实战中就无法充当触发器 ——
你会在需要决断的时刻改为临场判断,而临场判断正是这套系统要替换掉的东西。

**怎么让自己的触发线可判定,是你的策略问题**(见 `modes/_strategy.example.md`
「减仓 / 清仓」一节)。这里只提醒:设完线之后,回头检查一下过去几次触发判定
有没有落在模糊地带 —— 如果有,问题多半出在线的位置,而不是你的执行力。

## §7 词表与规则从哪里来

本项目**不内置任何交易理由标签或纪律规则**:

| 内容 | 位置 | 是否进仓 |
|---|---|---|
| 交易理由标签词表 | `config/reason-tags.toml` | 🔒 否(模板 `.example` 进仓) |
| 可检验的纪律规则 | `config/rules.toml` | 🔒 否(模板 `.example` 进仓) |
| 散文形式的策略手册 | `modes/_strategy.md` | 🔒 否(模板 `.example` 进仓) |
| 尺寸/现金/集中度等参数 | `config/profile.toml` | 🔒 否(模板 `.example` 进仓) |

**写台账时的 `reason_tag` 必须取自 `config/reason-tags.toml`。**
脚本会校验;写错会报错并列出可用值。不要凭记忆写标签,也不要自创。

查看当前生效的词表与规则:

```bash
make dashboard      # 纪律页显示你的规则是否被数据支持
make stats          # 同上,文本版
```
