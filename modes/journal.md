# Mode: journal — 尾盘交易日志(16:06 ET)

**此时正常时段已收盘,市价单无法成交** —— 本 mode 只做记录、压缩、和给次日留输入。
(盘后延长时段理论上仍可用限价单,但那属于 `check` + `trade` 的职责;
日志点不承担找机会的动作。)

**产出:** 追加条目到 `data/journal.md`(用户层,gitignore)+ 补齐 `data/trades.tsv`。

---

## Step 1 — 收口当日事实

1. `get_equity_orders`(当日)——**以券商记录为准**,不要凭记忆写当日操作。
2. `get_portfolio` + `get_equity_positions`——收盘后的最终持仓与现金。
3. 核对 `data/trades.tsv`:当日每一笔成交都必须有对应行。漏了就补,
   `reason_tag` 用 `config/reason-tags.toml` 里定义的标签。

```bash
make stats      # 顺手验证台账格式没坏
```

## Step 2 — 结构校验(先查再写)

```bash
make journal-check
```

脚本会检查 `data/journal.md`:

- 每个条目是否都有 `## YYYY-MM-DD` 标题(防孤儿段落)
- 条目是否严格**按日期倒序**(最新在最上)
- 全文总行数是否超上限
- 各条目是否符合分层压缩的行数分级

**为什么要脚本查:** 这两个 bug 都真实发生过——
2026-07-22 曾误锚定较早日期导致条目错序数日未察觉;
2026-07-31 曾在编辑中丢失一个 `##` 标题,正文变成挂在别人下面的孤儿段落。
`Edit` 工具返回成功只代表字符串替换执行了,**不代表文档结构是对的**。
现在这层由脚本兜底,不再依赖人眼。

## Step 3 — 写当日条目

用 `templates/journal-entry.md` 的结构。**新条目永远插在文件当前第一个 `##` 标题之前**
——插入前先确认当前第一条是哪天,不要凭记忆锚定。

条目必含五块:

1. **当日操作**——每笔:标的 / 方向 / 金额 / 成交价 / 占该仓位市值% / 理由。
   零操作也要写,并写清"每个候选被什么理由挡住"(逐个点名,不能笼统说没机会)。
2. **组合变动**——总值、现金/BP%、各标的占比、当日与累计浮盈亏。
3. **市场背景**——一两句:当日驱动 + TLT 方向及幅度 + 主线状态。
4. **反思**——今天哪个判断事后看逻辑站不住?哪个做对了但只是运气?
   **这一块最容易偷懒写成复述操作,要写"如果重来会怎么做"。**
5. **明日输入**——次日 `premarket` 能直接接手的:候选(方向/理由/触发参考)、
   blackout 名单、防守触发线。

## Step 4 — 分层压缩

```bash
make journal-compress
```

脚本给出压缩指令,你负责写摘要。分层规则:

| 条目年龄 | 保留粒度 |
|---|---|
| 最近 3 个交易日 | **全细节** |
| 3 日 ~ 2 周 | 压成**单行摘要**(日期 + 最关键的一个判断或操作) |
| 超过 2 周 | 按周/按轮**合并成一行** |

硬约束:

- **全文行数上限**由 `journal.max_lines`(`config/profile.toml`)控制。
- **不能只压"窗口外最老的那一条"。** 每天做"新增 1 条 + 压缩 1 条"的单进单出置换,
  行数还是会缓慢累积(2026-08-05 一路涨到超限 25 行才被发现)。
  超限时**一次性**把 >2 周的多条合并成按周摘要。
- **教训要去重**:已经写进 `modes/*.md` 纪律的内容,日志里不再重复叙述,只留一句指针。

压缩完再跑一次 `make journal-check` 确认结构完好。

## Step 5 — 活文档回写(容易漏,别跳过)

问自己:**今天有没有值得写进纪律手册的东西?**

| 情况 | 写到哪 |
|---|---|
| 新踩的坑 / 新犯的错(策略判断) | `modes/_strategy.md` + `config/rules.toml` |
| 被结果验证有效的新做法 | 同上;规则 `status` 可考虑升级 |
| 值得反思的判断点(结果对了但逻辑站不住) | 同上,追加进该规则的 `evidence` |
| 平台机制变化(权限、工具行为、结算规则) | `modes/_mechanics.md` |

**触及了哪条规则,就在那条规则的 `evidence` 里追加一行**(带日期与结果)——
这是复盘时审计器能拿到证据的唯一来源。

**今天只做证据累积,不做状态变更:**

| 动作 | 今天做 | 说明 |
|---|---|---|
| 往规则的 `evidence` 追加一行 | ✅ | 带日期与结果,这是复盘的输入 |
| 更新 `last_audited` | ❌ | 那是 `review` 审计后才做的 |
| 改规则 `status`(升/降级) | ❌ | 必须经 `review` 用数据审计 **且用户批准** |
| 删掉被推翻的规则 | ❌ | 降为 `refuted` / `retired`,**保留记录** —— 免得半年后把同一条当新发现再写一遍 |
| 动 `CHANGELOG.md` / `VERSION` | ❌ | **策略变更不进系统层版本日志**;只有平台机制或代码变化才动它们 |

若今天的经验属于**平台机制**(权限、工具行为、结算规则、调度),那才写进
`modes/_mechanics.md`,并按 `AGENTS.md` §6 记 `CHANGELOG` + bump `VERSION`。

